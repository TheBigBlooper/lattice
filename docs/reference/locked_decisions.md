# Lattice - Locked Decisions

An **append-only, numbered** registry of decisions the founder has fixed. Grouped by area under `###` headings. Each entry states the locked value plus a one-line rationale. **Append only** - never renumber or delete an entry; a superseded decision is struck by a new, higher-numbered entry that references it. The `Lock` column is `Hard` (needs an explicit unlock to change) or `Soft` (a default, changeable with less ceremony).

> Only the stack + architecture facts the founder has already fixed are recorded here. A design question that is still open is a **GitHub issue carrying the `design` label**, not an entry in this file - see [Open design questions](#open-design-questions) at the bottom.

### Technical Stack

> **Stack rationale (why these):** Java 21 + Vert.x 5 give a reactive Java Virtual Machine service tier without a heavier framework; Maven multi-module keeps the contract, common library, and services building as one tree. The React status console is a thin operator view, not a product surface.

| 67 | **Elasticsearch indices set `auto_expand_replicas: "0-1"`, and cluster status maps green -> `UP`, yellow -> `DEGRADED`, red -> `DOWN`.** The mesh-gateway polls `GET /_cluster/health` directly. **Extends #32.** | Two defects, one fix each. The health signal did not exist: the readiness check every data-owning service registers is a client ping, so a **red** cluster - primaries unallocated, data genuinely unavailable - answered it and was reported `UP`, meaning a baseline would announce itself ready while unable to serve. And the reading a real probe would return locally is permanently yellow, measured: three active primaries, three unassigned replicas, every index at one replica on a single node. | 80 | **A baseline reports the state of each of its broker's federation links, measured per peer from the broker rather than inferred from peer silence.** It rides `Peer` as an optional `up`/`down` field, and the Artemis infrastructure row is **derived from those states** rather than probed separately, so the two can never disagree. The console renames what an operator sees to **Broker** (gateway to its own broker, the contract's `meshLink`) and **Federation** (broker to peer brokers); neither is called "mesh". The Discovered Mesh table gains a **Federation column** rendering `Up`/`Down`/`Refused`, each with a **keyboard-reachable tooltip**, and a refused peer produces **one** activity entry rather than two. Reporting is **neutral**, sharpened to `Refused` only when the baseline's **own** certificate has **expired** - read by completing a TLS handshake against its own broker, because Artemis management exposes nothing about its certificate and a mounted copy would both distribute TLS material and be able to disagree with what the broker loaded. Revocation is **not** knowable locally, so a revoked-but-unexpired certificate reads `Down`; a proactive expiry warning is in scope. A per-peer gauge is added, and `revoked-east` + `foreign-authority` assert the whole thing. **Extends #46 and #66; #42, #43 and #46 are untouched.** | There were two links and only one had a name, so the console reported a healthy mesh link while nothing crossed: a revoked baseline showed `meshLink: up`, Artemis `UP`, and every peer `UNREACHABLE` - indistinguishable from a mesh that had merely gone quiet, on the one baseline whose fault it was and whose re-issue would fix it. Measured beat inferred on a property discovered rather than assumed: each broker already carries one federated queue per peer with the peer's cluster id in its name, so the truth is **per peer**, and the cheap inference ("every peer aged out while my own link stayed up") is mesh-wide, cannot fire when one peer is refused and another is fine, is wrong when every peer genuinely did go down together, and reports an inference in the shape of a measurement. Both surfaces rather than one because either alone is worse - the peer field is easy to miss since a refused row reads `UNREACHABLE` regardless, and the Artemis row alone flattens a per-peer fact into prose - and deriving one from the other is what stops two renderings of one fact drifting apart. No `unknown` state, because the case it would name (the broker link is down, so federation cannot be read) already carries a banner explaining exactly that, matching #66's refusal to distinguish unreachable from dead. The rename is the fix for a sentence that would make an operator distrust the screen, and collapsing both readings into one "Mesh" was rejected for re-creating the ambiguity #46 removes. A column beat annotating the existing `UNREACHABLE` cell, and only after both were drawn: **federation drops a full peer time-to-live before the peer does**, so an annotation living inside that cell has nowhere to appear during the ~30 seconds when the cause is knowable and the symptom has not arrived - it can only ever explain a failure after the fact. The column also reports the absence of the problem usefully, since a peer that is unreachable with federation `Up` reads immediately as somebody else's fault. Its costs are accepted rather than argued away: permanent width in the densest panel (smaller than first assumed - the panel is about 900px at a 1440px window), and a column that reads `Up` on every row almost always, which is the sharper cost because a column that never changes is one the eye learns to skip. Neutral-then-sharpened is the only option that earns the stronger wording instead of guessing it: the signal is symmetric and its meaning is not, since hub-east and hub-central observe the identical dead link and only one of them can act, and blame inferred from the pattern is wrong exactly when a baseline has a single peer. Expiry falls out of the same local check and is the only part of this that prevents an outage rather than explaining one, on a date nobody is watching. **Signing the operator out is rejected outright**: operator identity and broker identity are deliberately separate, and removing someone's access removes the one tool that would show them the problem - the same reasoning that keeps the gateway `UP` on broker loss (#42). Two risks are carried rather than hidden: the read depends on Artemis's federated-queue **naming**, a broker implementation detail whose rename would make the signal fail **to healthy** - the exact shape of the stale-gauge and never-passing-hook defects - which is why the scenario assertions exist and are documented as the mitigation rather than as coverage; and revocation is invisible to a local check, so the sharpened wording fires on expiry alone and the neutral reading says what it ruled out rather than claiming the certificate is fine. Both mechanism questions were **measured rather than assumed**: management over the AMQP head works and is pinned by a permanent suite, and management exposes nothing at all about the broker's certificate, which is what forced the handshake read. Detail in `federation_link_visibility.md`. | Soft |

| 76 | **CI triggers on `push` only, to `dev` and `lat-*` branches. Cancelling the duplicate through a shared concurrency group was the obvious alternative and is worse: a cancelled run reports `cancelled` rather than `success`, so it can sit on the head commit as an unsatisfied required check and block the merge - trading wasted minutes for a stuck one. ### Open design questions

**An open design question is a GitHub issue carrying the `design` label, not a row in this file.** It is picked, prioritized and closed like any other ticket; the design session's output is a new numbered decision above plus the document that decision points at.

This replaces a table of placeholder questions that numbered them `P1` through `P8`. Those numbers named a conversation rather than anything in the product, which made them useless to a reader holding only the repository - the same reason the [code commenting standard](../protocol/core_protocol.md#code-commenting-and-docstrings) permits `locked #NN` and forbids issue and session references in source. The trail the table carried is not lost: it lived in the decisions themselves all along, which supersede each other by number and say so in their own text. The interop question, for instance, reads as #30 marked superseded and #37 saying what it supersedes and why - which is the same history the table restated at one remove.
