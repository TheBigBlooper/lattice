# Lattice - Locked Decisions

An **append-only, numbered** registry of decisions the founder has fixed. Grouped by area under `###` headings. Each entry states the locked value plus a one-line rationale. **Append only** - never renumber or delete an entry; a superseded decision is struck by a new, higher-numbered entry that references it. The `Lock` column is `Hard` (needs an explicit unlock to change) or `Soft` (a default, changeable with less ceremony).

> Only the stack + architecture facts the founder has already fixed are seeded here; deep design questions that are explicitly deferred to a future design session live in the **Planned - design session** group at the bottom as placeholders, NOT as locked decisions.

The React status console is a thin operator view, not a product surface.

### Mesh + Interop

> Promoted from planned questions P1-P4. Each row is the one-line decision; the full design lives in [docs/design/architecture/](../design/architecture/_index.md).

| #  | Decision                                                                          | Rationale (one line)                                                                       | Lock |
|----|-----------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------|------|
| 29 | **Mesh discovery + peer liveness** (announce with `consoleUrl`/`apiBaseUrl`, multicast addressing, 30s TTL). | Decentralized self-discovery over Artemis; detail in `mesh_discovery.md`.                  | Hard |
| 30 | **Cross-cluster interop: canonical envelope + per-cluster gateway translation.** _(SUPERSEDED by #37 - Shape A: no work crosses the mesh, so there is no canonical translation.)_  | Divergent local models interoperate via the shared contract; detail in `cluster_interop.md`. | Hard |
| 31 | **Mesh envelope schema + versioning** (common header + typed JSON payload, records). | One versioned wire format tolerant across peer baselines; detail in `mesh_envelopes.md`.   | Hard |
| 32 | **Per-service Elasticsearch data model** (index-per-entity, aliases, bootstrap).  | Single-writer indices with zero-downtime mapping evolution; detail in `data_model.md`.     | Hard |
| 36 | **Order-of-record stays with originator; interop console is mesh-mediated.** _(SUPERSEDED by #37 - Shape A: each baseline owns its own orders; federation is UI-redirect, not mesh-mediated.)_      | Peer fulfills only, not owns; console drives A->mesh->peer. See interop_console.md.        | Hard |
| 37 | **Shape A federation: each baseline owns its own data (orders); interop is a UI redirect to the owning baseline + a unified read-only live-pull view; the mesh carries discovery + endpoint advertisement only.** Supersedes #30 + #36. | Act on the owning baseline (redirect to its `consoleUrl`); no work or translation crosses the mesh; unified view live-pulls each peer's `apiBaseUrl`. Detail in `cluster_interop.md` + `interop_console.md`. | Hard |
| 42 | **The `mesh-gateway` service is the sole mesh participant**: one announcement and one registry per cluster, serving `getPeers` + `getBaseline`. Its peer registry is **in-memory only** (retiring the anticipated peer-registry index), its `/readiness` stays **UP** when the broker is unreachable, and it runs a **single replica** for MVP. | Announce logic in `BaseVerticle` would make every service announce under the same cluster id and hold its own divergent registry. The registry is derived state that peers re-announce every heartbeat, so persistence buys little and adds a dependency this service otherwise does not need; staying UP on broker loss keeps the console served with an honest degraded view instead of nothing. Detail in `mesh-gateway.md`. | Hard |
| 43 | **Cluster `health` is a polled rollup of the cluster's services** (`ready` / `degraded` / `down`), from a configured `CLUSTER_SERVICES` readiness list. The rollup travels on the mesh; the per-service breakdown is served only on `getBaseline`. | The gateway's own readiness can never fail (no datastore, and broker loss deliberately does not fail it), so announcing it would put a constant meaningless `ready` on the wire. Keeping the breakdown off the mesh stops the envelope growing per service and stops the mesh drifting from discovery into status replication. | Hard |
| 44 | **Every baseline runs its own Artemis broker, joined to its peers by Artemis *federation* (not clustering)**: address federation on the multicast `lattice.mesh.announce` address with `max-hops="1"`. A **joining** baseline declares both `upstream` and `downstream` connections to each peer, so existing baselines discover it with **no edit, restart, or redeploy**; every broker carries a generic `downstream-authorization` role naming no peer _(this clause is CORRECTED by #47 - no such attribute exists in Artemis 2.44; the guarantee stands, the mechanism is ordinary broker security)_. `ARTEMIS_URL` stays **single-valued** (services only ever address their own broker). | A single shared broker, owned by one baseline or dedicated, is a single point of failure that stops all discovery - the practical equivalent of the central registry decentralized discovery exists to avoid. Federation, unlike clustering, is built for independent brokers in separate administrative domains with differing versions, which is what baselines are (#12, #14); clustering's discovery groups also rely on multicast over User Datagram Protocol, which does not cross Kubernetes pods or sites. Downstream configuration is what makes onboarding cost linear and paid by the joiner instead of quadratic across every existing broker. Detail in `mesh_broker_topology.md`. | Hard |
| 45 | **The mesh federation credential is one shared role per environment** (delivered as a Secret) for MVP; per-baseline broker identity is deferred to the per-baseline identity work. _(The deferral is RESOLVED by #50 - a per-baseline certificate signed by a shared authority; the shared credential stands until that build lands.)_ | A per-baseline broker user would have to be authorized on every existing broker, breaking the no-edit-on-join property #44 is built to guarantee. The leak risk is bounded by Shape A (#37): the mesh carries discovery only, so a forged announcement can advertise a cluster that is not there but cannot move any data. Interim by design; #38 covers REST authentication only and says nothing about the broker. | Soft |
| 46 | **A baseline's mesh-link state is served on its own API only and never announced.** | An operator must be able to tell "we are cut off" from "the peers are gone": a broker outage ages *every* peer out at once, which naively renders as a total peer outage. The signal cannot ride the mesh for the same reason as #43 - a report about a broken link cannot travel over that link. | Hard |
| 47 | **A peer's downstream federation command is authorized by ordinary broker security, not a `downstream-authorization` setting.** Every Lattice broker grants a shared `lattice_federation` role the same permissions as its own services; the joining baseline presents that role's credential via `user`/`password` on its `<federation>` element. **Corrects the mechanism clause of #44**, which specified a `downstream-authorization` attribute on `<federations>`. | No such attribute exists in the pinned Artemis 2.44.0 schema: a broker configured with it fails validation and does not start. This is what the schema actually supports, verified by running two federated brokers. The *property* #44 exists to guarantee is untouched and now demonstrated - an existing baseline's broker names no peer, is never edited on join, and still federates on command. #45 (one shared credential per environment) is unaffected; this only corrects where that credential is declared. Detail in `mesh_broker_topology.md`. | Hard |

> Tunable timing defaults (heartbeat 10s, peer TTL 30s) are config-driven (env), documented in the design docs; the decisions above (the approach) are Hard, the numeric defaults are Soft.

> **Envelope version negotiation (RETIRED under #37).** The former refinement of #29 + #31 - a `ClusterAnnouncement` advertising `supportedEnvelopeVersions` so a sender could down-emit the highest version a recipient supports, with a NACK backstop - existed to make **directed handoffs** degrade across a breaking change. Shape A removes the directed layer, leaving only the unsolicited multicast `ClusterAnnouncement`, whose additive forward-compatibility (ignore unknown fields) needs no negotiation. `supportedEnvelopeVersions` is no longer advertised; negotiation can return if a directed request/reply type is ever added. Detail in `mesh_envelopes.md` + `mesh_discovery.md`.

### Auth

| #  | Decision                                                                                                          | Rationale (one line)                                                                        | Lock |
|----|-------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|------|
| 38 | **Per-baseline Keycloak** (each baseline its own realm, roles + groups); a redirect to a peer authenticates against that peer's Keycloak; re-auth per baseline for MVP. | Identity stays with the baseline that owns the data (Shape A); cross-baseline single-sign-on via realm brokering is a future refinement. Promotes P5; build is its own ticket. | Hard |
| 48 | **Realm shape + protected surface**: two roles (`viewer` = every GET, `operator` = + writes) with matching groups; **all `/api/v1` protected on every service, `/health` + `/readiness` left open**; console is a **public client using PKCE**, services are **bearer-only** validating against their own realm's JWKS via `vertx-auth-oauth2`; the realm is provisioned by a **committed import file** and Keycloak runs **dev-mode + unpersisted** locally. One Keycloak **per baseline, including locally**. | The line that matters is who can change state, so two roles cover it; an `admin` role would grant exactly what `operator` does until an admin surface exists. Probes cannot carry a token, so gating them trades real availability risk for no secrecy. Bearer-only means no per-request Keycloak call, so a Keycloak outage does not invalidate issued tokens. Import runs only when the realm is absent, so persistence would silently ignore edits - the same trap the Artemis `etc-override` config hit. A shared local Keycloak would repeat the shared-broker mistake #44 removed. Detail in `per_baseline_identity.md`. | Hard |
| 49 | **Role and group names are standard across every baseline; membership is deliberately unsynchronized.** An operator working across N baselines holds N grants, and a redirect may legitimately land on a login they cannot pass. | Standard names make a token interpretable wherever it was issued and reduce future realm brokering to a role mapping. Matching *membership* cannot be enforced without baselines synchronizing user directories - the exact cross-baseline coupling Shape A (#37) removes - and would override each baseline's right to decide its own access (#12, #14). The consequence is a documented cost, not a defect. Detail in `per_baseline_identity.md`. | Hard |
| 50 | **Broker identity is a per-baseline X.509 certificate signed by a shared Lattice certificate authority, with mutual TLS between brokers; authorization remains a single generic role.** **Resolves the deferral in #45.** | Trusting the authority rather than individual peers is what preserves #44's no-edit-on-join: the trust anchor names nobody, so a joiner's certificate is accepted with no edit anywhere. It buys traceable identity and individual revocation (via the revocation list, no peer edits) over one shared credential, and closes transport security between brokers as a bonus. Authorization must stay generic because Artemis's certificate login modules map a specific distinguished name to a role, so per-peer permissions would be edit-on-join by another route; federation is symmetric (#44), so nothing needs them. Detail in `per_baseline_identity.md`. | Hard |

| 39 | **Logging: SLF4J facade + Logback binding; Vert.x routed through SLF4J** (one pipeline).                | One logging engine (#15); parameterized, levels ERROR/WARN/INFO/DEBUG, no printStackTrace; detail in core_protocol.md. | Soft |
| 40 | **Supply-chain scanner: OSV-Scanner** (pinned binary, its own CI job on the `dev` -> `main` PR), scanning the **Maven-generated CycloneDX SBOM** rather than the poms. Replaces OWASP Dependency-Check; supersedes the OWASP clause of #33. | OWASP downloaded the whole NVD catalog locally (needing an API key, 15+ min, and failing on NVD rate-limit 429s); OSV-Scanner queries osv.dev in seconds with no key. It must read an SBOM because remote (deps.dev) resolution cannot see our unpublished SNAPSHOT modules and silently drops the entire graph. Accepted gap: test-scoped deps are excluded from the aggregate SBOM (not shipped in runtime images). | Soft |
| 41 | **Mesh transport client: `io.vertx:vertx-amqp-client` (AMQP 1.0)**, not the Artemis CORE/JMS client. The announce address is addressed as a **topic** so announcements fan out to every peer. | Vert.x-native and non-blocking, so the mesh never needs `executeBlocking` to stay off the event loop; the version rides the vertx-dependencies BOM so it cannot drift (one engine per job, #15). Artemis serves AMQP on the same 61616 acceptor as CORE. Topic addressing is load-bearing: treated as a queue, the broker would load-balance announcements and each peer would see only a fraction of the mesh. | Soft |
| 51 | **Status-console quality gates: Biome (lint + format), Semgrep (registry packs + a committed `.semgrep/lattice-rules.yml`), knip (dead code), Vitest (+ coverage)**, run by a single `verify` script in the console package that the **pre-push hook invokes after `./mvnw verify`**. Package manager **pnpm**, Node 24. | The console is the first non-Java surface, so it needs its own gate set - but not its own gate *philosophy*: #28 makes the local pre-push run the primary gate because this repo is on GitHub Free minutes, so the console's checks run there too rather than in CI. One tool per job (Biome replaces a separate formatter + linter, mirroring Spotless + Checkstyle on the Java side). Keeping the console out of Maven leaves its inner loop at Vite speed and its Node version in `.nvmrc` rather than a pom; the cost, accepted, is that the hook runs two commands instead of one, so it fails loudly rather than skipping when the console's dependencies are absent. | Soft |
| 52 | **OSV-Scanner also scans the console's `pnpm-lock.yaml`**, alongside the Maven-generated CycloneDX SBOM. Extends #40. | The SBOM is generated by Maven and therefore contains no Node packages: left alone, the console's entire dependency tree would be invisible to the supply-chain gate. That is the same class of silent blind spot #40 was written to close when scanning the poms reported a clean result while resolving nothing. | Soft |
| 53 | **The pre-push hook is scope-aware**: it reads the paths changed in the commits being pushed and runs only the gates those changes can affect (the Maven reactor for Java + build config, the console's `verify` for console code, neither for a docs-only push). When it cannot determine the range it runs **everything**. **Refines #28**; the hook remains the primary gate and is not replaced by a documented manual step. | Running the full reactor to push two markdown files taxes the most common commit in the repo, and a gate that is tedious in the common case invites `--no-verify` as a habit - which costs far more than it saves. Making the gate a documented pre-commit step instead was considered and rejected: that converts enforcement into discipline, and with CI running only on the `dev` -> `main` promotion, the first forgotten run lands breakage on `dev` and is found late. Erring toward over-running when the range is unreadable keeps a wrong guess expensive in time rather than in correctness. | Soft |

| 54 | **Kubernetes tooling: Helm**, not kustomize. One chart at `deploy/k8s/chart`; **one release installs one baseline**, and rendered output belongs under `deploy/k8s/generated/`. The Keycloak realm ConfigMap is **generated from the committed realm file** (`.Files.Glob ... .AsConfig`), which is why that file now lives inside the chart and docker-compose mounts it from there. | Baselines differ by *values*, not by patches: the same manifests with a different cluster id, realm hostname, and console URL. That is what a values file expresses directly and what a kustomize overlay expresses as a diff against a base - and a diff is the harder thing to read when the question is "what is hub-east actually running". Helm also templates the realm ConfigMap from the committed JSON, which kustomize's `configMapGenerator` can also do, but Helm additionally gives release lifecycle (`upgrade`, `rollback`, `history`) that the deploy rungs in `deploy_protocol.md` already assume. The accepted cost is Go templating in YAML, which is genuinely worse to read than plain manifests; it is contained by keeping logic in `_helpers.tpl` and by having one templated service definition rather than one per service. The realm file had to move into the chart because Helm cannot read outside the chart directory - a chart that reached out could not be packaged, and `helm package` would have produced a tarball that silently installs an empty realm. | Soft |
